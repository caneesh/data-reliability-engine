# Code review, 2026-10-13: release 3 (extensibility) and the engine around it

Five reviews ran in parallel, each on one aspect (functional correctness; hard constraints, data leakage and performance; SQL from configuration; design and readability; tests and documentation), each working from the code and required to trace every claim. This page is the consolidated result. Findings marked **verified** were reproduced by hand on this branch (`8c8571b`); the rest were traced through the code by the reviewer and read again here.

**Status (2026-10-13):** A1 to A11 and the two lower items are fixed, each with the test named below: A1 and A4 in `9591b1e`, A2, A3, A5 and A6 in `1243f93`, A7 and A8 in `614a5b3`, A9 to A11 in `7eac24e`; the documentation drift in section C in the commit after those. The design pass (section B) is done in `9b3592d` (B1, B6), `d74e5c8` (B2, B3), `7fdc435` (B5), `85d10f8` (B4) and the commit after those (B7, with the R12 watchdog flake that failed CI run #40); B9 was fixed with A1. Left open on purpose: B8 (type hints) and B10 (a lighter watchdog load), and `_check_check_params` keeps its dataset placeholder. Decisions taken while fixing are in `docs/decisions.md`, "Code review of release 3".

**Verdict.** The engine's core is sound: the one write path, the three result states, the append-only store and the guard tests all hold, and nothing in release 3 writes, drops or moves anything. The defects are at the edges that release 3 opened: the order in which configuration is validated against the registries, what `dre guard` exempts when it runs over a tree that is not the engine, two SQL constructs the "query-only" wrap does not stop, and one check (T1_FRESHNESS) that is not bound to its window. Eleven items should be fixed before release 3 is merged to `main`; the design items are worth a follow-up pass.

## A. Fix before merging (defects)

| # | Severity | Finding | Where | Fix |
| --- | --- | --- | --- | --- |
| A1 | **High** (**verified**) | Configuration SQL can run more than a query. Inside `SELECT * FROM (...) dre_rule`, Spark accepts `java_method`/`reflect` (calls to Java static methods) and `TRANSFORM ... USING '<program>'` (runs an external program on the executors). The keyword scan does not list them, and `feed_filter`, `hop_exclusions`, `open_when` and probe `condition` fragments are not scanned at all. Configuration is a trusted, reviewed artefact, so this is defence in depth, not an open door; but guard rule 10 claims more than it delivers. | `checks/rules/conf_template.py` `_FORBIDDEN`; `config/models.py` `_sql_fragment` (rejects only `;`) | Add `TRANSFORM`, `USING`, `java_method`, `reflect` to the scan; run the scan over every SQL fragment from configuration (one `forbidden_sql(text)` used by `_sql_fragment` and `check_template_file`); say in spec section 9 what the wrap does and does not stop. |
| A2 | **High** (**verified**) | An extension's notification sink can never be configured: `notify:` entries are validated against `SINKS` inside `Defaults.model_validate`, before `extensions:` load, so `defaults` fails to load and nothing starts. The spec's "a webhook sink is a module that registers itself" is unreachable from configuration. | `config/models.py` `_sink_config`, `Defaults.notify`; `config/loader.py` `load()` order | Read `extensions:` from the raw mapping and load them before `Defaults.model_validate`; or make `notify` a plain list and validate it in `cross_check` after the extensions load. Test: the example extension's `x_pigeon` under `notify:`. |
| A3 | **High** (**verified**) | A required parameter missing from a feed-level `check_params` passes `dre validate` ("missing" is skipped at feed level on the assumption the dataset reports it, but the dataset loop only sees the dataset's own keys). The check is planned and is DID_NOT_RUN / invalid_config on every dataset of the feed, every run. | `config/validate.py` `_check_check_params` | At dataset level, validate the merged parameters for every check the pattern lists that any level configures; report a missing field on the dataset (or on the feed when the dataset has no entry). Test: feed-level `T1_COLUMN_RANGE: {min: 1}` is an error. |
| A4 | **High** (traced; two reviewers) | `dre guard` grants any tree the engine's own path allowances: a file whose path ends in `hcsc/datalake/dre/store/writer.py` may use the write API, `.../store/ddl.sql` may CREATE, `.../store/local_setup.py` may CREATE DATABASE, and `.../hcsc/datalake/dre/guard.py` is skipped entirely. An extension package can inherit all of them by naming its files that way. | `guard.py` `scan_text`/`scan_tree` (`endswith` allowances, `GUARD_MODULE` skip) | `scan_tree(root, allowances=False)` from `guard_command`: no privileged paths, no skipped file. For the engine's own scan, match the exact path relative to `src/`, not a suffix. Tests: the three decoy files under `tmp/ext/hcsc/datalake/dre/...` all flagged. |
| A5 | **Medium** (**verified** by two reviewers) | A malformed `conf/patterns/<name>.yaml` that a feed actually uses crashes `dre validate` (and `dre run` via `runner._load`) with a traceback: `_check_patterns` records the error, then `_check_probes` and `_check_check_params` call the pattern functions again and the `ValueError` escapes. The existing test writes the bad pattern under a name no feed uses. | `config/validate.py` (`probe_keys(feed.pattern)`, `pattern_check_ids(...)`) | `_check_patterns` returns the broken names; skip the pattern-dependent checks for feeds on them (one error, on the pattern file). Test: a bad `table_merge.yaml` override with the second feed on it. |
| A6 | **Medium** (traced; three reviewers) | An extension that fails half-way through import leaves what it registered before the failure in the registries, unrecorded in `_LOADED`, so `unload` cannot remove it; a second `load()` then reports a misleading "registered twice". Also `load()` never unloads extensions a new conf does not list (long-lived drivers, notebooks, tests). | `extensions.py` `load_extensions` | On failure, unregister `ids_now − before` for every registry and drop the module from `sys.modules`; in `load()`, unload extensions not in the current list. Test: a module that registers a check then raises. |
| A7 | **Medium** (**verified**) | T1_FRESHNESS is not bound to its window: `MAX(time)` runs over the whole table, so a RERUN or REPLAY of a historical window compares the table's current latest time with a past window end (negative age, always PASSED) and the answer changes over time. The module docstring's claim that "a RERUN answers for its window" is false. | `checks/sql/t1_freshness.sql.j2`, `tier1/freshness.py` | Add `WHERE time_expr < window_end` (the same time kind the check already compares with, so not a cross-kind comparison). Test: RERUN of a historical window reports the age at that window end. |
| A8 | **Medium** (**verified**) | T1_COLUMN_RANGE with `min`/`max` on a string column silently passes non-numeric values (`'abc' < 1.0D` is false both ways with ANSI off), so a column of garbage PASSes. Also `min`/`max` together with `allowed` are ANDed (the spec says "or"), and `allowed` compares `CAST(col AS STRING)`, so `allowed: ["1"]` does not match a DOUBLE `1.0`. | `checks/sql/t1_column_range.sql.j2`; spec section 6 | Cast once (`CAST(col AS DOUBLE)`) and count a non-null value whose cast is null as a violation; either refuse `allowed` together with bounds in `ColumnRangeParams` or state the AND semantics and the string-form comparison in the spec. Tests on a DOUBLE column. |
| A9 | **Medium** (traced) | Conf-template parameter `default`s are not validated against the declared type (`validate_default` is off), so a default such as `"a b; DROP TABLE x"` on a `column` param, or `"abc"` on an `int`, reaches the template; the wrap makes it a parse error at run time rather than a `dre validate` error. | `checks/rules/conf_template.py` `params_model` | `Field(default=..., validate_default=True)`; scan string defaults with the same `forbidden_sql`. |
| A10 | **Medium** (traced) | `check_template_file` raises a `PydanticCustomError` (a `ValueError`, not a `ValidationError`) when the params model cannot be built, out of a loader block that catches `ValidationError` only: a traceback instead of file and line (reproduced by one reviewer with a param named `model_config`). | `conf_template.py` `check_template_file`; `config/loader.py` `_load_templates` | Return a `SqlProblem` (with the `params` line) instead of raising. |
| A11 | **Medium** (traced) | The `stdout` sink prints the whole digest body into the run's stdout, which is the scheduler's log. The body carries `group_by` data values and, with `email_sample_keys`, key hashes: allowed in email, but hard rule 6 says logs carry counts, check ids and table names only. Before release 3 the "no relay" path printed one status line. | `notify/sinks.py` `StdoutSink` | Print the subject and the per-check lines without group values and samples, or require `full_body: true` on the sink and say what it exposes. |

Two lower items worth doing in the same pass: `Registry._load` sets `_loaded = True` before importing, so a failing built-in import leaves a permanently partial registry (set it after the loop); and the collision message for a conf template or calendar says "is a packaged X" even when the id came from an extension (use the registered origin).

## B. Design and maintainability (follow-up pass, no behaviour change)

Ordered by payoff. None of these change SQL, result states or the guard rules.

*Outcome:* 1 to 7 and 9 done, with the full suite and the e2e run after each commit; 8 and 10 left open (see the status line). Item 4's `_check_check_params` was not split further: after pass 2 it is one locate-and-report loop over the merged parameters, and the dataset placeholder stays because `configured_params` takes a dataset.

1. **Three copies of the same "conf set" lifecycle.** `use_conf_patterns` / `use_conf_templates` / `use_conf_calendars` and the two `_CONF_IDS` globals are one algorithm written three times, and `loader._load_templates` / `_load_calendars` are the same thirty lines with the words swapped. Give `Registry` a `replace_conf(items) -> refused` method that owns its conf ids, and the loader one `_load_conf_registry(folder, model, registry, build)`. One `reset_conf_state()` for tests replaces three per-module autouse fixtures.
2. **`checks/registry.py` is two modules.** The check registry (`CHECKS`, `register_check`, `checks_for`) and a pattern-file reader (globbing, `kind`, caches, cause-list validation, `probe_keys`). Split the latter into `checks/patterns.py`; move `configured_params`/`resolve_params` out of `checks/base.py` next to it, which also removes the two-way lazy import between `base` and `registry`.
3. **Lazy imports that hide dependencies.** `runner.py` has fifteen function-level imports and `validate.py`/`loader.py` several more, none of which break a cycle. Hoist them. Keep the ones in `config/models.py` (validators consulting registries: the one deliberate upward dependency, worth a docstring saying so) and in `cli.py` (keeps `--help` free of PySpark).
4. **Long functions.** `validate.cross_check` (~225 lines, seven concerns), `runner.run` (~110 lines, with a three-level write/mark-incomplete chain), `loader.load`, `validate._check_check_params` (four copies of locate-and-report, a `SimpleNamespace` stand-in for a dataset). Each has an obvious split the design reviewer named; `_check_check_params` gets simpler once `configured_params` takes the two raw dicts instead of the models.
5. **Names.** `params` means a model type, an instance, raw YAML and (in `CauseEntry`) a string key: rename `CauseEntry.params → params_key`, `TemplateSpec.params`/`Probe.params → params_model`. `kind` is used for a registry label, a cadence kind, a pattern kind, a sink kind, the loader's directory table and an object type: rename the cheap ones (`Registry.kind → label`, `loader.KINDS → OBJECT_DIRS`, pattern `KINDS → PATTERN_KINDS`).
6. **Dead code and stale text.** `conf_template_ids()`, `probe_types()`, `notify/email.send()` have no callers; package docstrings still say "(build step N)"; `validate.py`'s header describes release 1; `Calendar.origin` comment says "packaged or conf" but the example extension registers "extension" (make it a `Literal`).
7. **Private access across modules.** `validate.py` imports `_conf_names` and `_pattern_checks` from the registry; tests clear `registry._pattern_checks` eleven times and `del PROBES._items[...]`. Make the needed functions public and give tests one `pattern_yaml(text)` fixture.
8. **Type hints.** `Any` where the type is at hand: `CheckContext.params`, `required_columns(params)`, `TemplateSpec` callables, `Probe.run`, `SinkKind.build`, `Config.templates/calendars`, `validate._check_check_params(feed, ds)`.
9. **`_FORBIDDEN` matches inside string literals and comments** (`status = 'LOAD'`, a column named `cache`), rejecting legitimate templates. Strip literals and comments before matching, since the wrap carries the real guarantee.
10. **Watchdog weight.** `watchdog.watch` now runs the full `load()`, which imports extensions and compiles templates before reading `dq_run`; an extension that blocks at import stalls the component meant to notice stalls. A `load_defaults()` path for the watchdog would keep it light.

## C. Tests and documentation

**Tests to add** (the important ones): A1–A11 each need the test named in the table. Beyond those: `deliver` with two sinks where the first raises; the testing kit's negative paths (`probe_contract` on a probe that raises currently passes, because the engine turns it into ERROR; `template_contract` on a template missing `violations`); a `kind: file` conf pattern end to end with landing fixtures; a conf calendar end to end (T1_ON_TIME over a window containing a holiday); the conf template helpers and param types not yet exercised (`column`, `key_expr`, `number`, `columns`, `sql`, `int`, `float`, `bool`); `load()` twice with different conf dirs.

**Weak assertions to tighten:** the `guard.py` exemption test checks three substrings (an AST check of imports and calls would hold the exemption to its claim); `"does not parse" not in out` after `dry-run` would pass if dry-run stopped rendering templates (add the positive case); `assert e.field == "" or "landing" in e.fix`; `fix in e.fix + e.problem`; the email sink test that depends on a hostname not resolving (monkeypatch SMTP as `test_email.py` does); several `e.line >= 1` where the exact line is known.

**Documentation drift** (all small): `docs/handoff.md` still says "Tests: 515" (617) and the step 8 row cites a commit SHA from before an amend (`a8a0107` is right); spec section 2 says a feed's pattern "must be a packaged pattern file" (conf patterns too) and "five kinds of capability" (seven registries); spec section 3 lists four template helpers (there are five: `number`); section 8's command table lacks `dre guard` and its exit codes; section 2's tree lists `sources/scheduler.py`, which does not exist, and omits `checks/derived.py`; section 6 should state T1_COLUMN_RANGE's AND semantics once A8 is decided.

## D. What was checked and found sound

Every `detail`, `observed`, `expected`, log line and evidence dict in the new code carries counts, config values, field names or exception types only; pydantic messages embed config values, never table values. The `SELECT * FROM (...) dre_rule` wrap does make DDL and DML a parse error (verified), and `WITH ... SELECT` inside it works. `load()` ordering is right for patterns, templates and calendars (only `notify` and `extensions` are out of order, A2). `resolve_params` merges pattern → feed → dataset correctly, and table-wide datasets read `table_wide.yaml` defaults. The cause engine turns an unknown builtin code into an ERROR row and rejects it at pattern load. T1_COLUMN_RANGE is window-bound, so RERUN is reproducible for it. CLI exit codes are consistent. The pattern caches are cleared on every `load()`. The guard tests still run every CAUGHT/ALLOWED snippet against the package scanner, so a weakened pattern still fails CI.
