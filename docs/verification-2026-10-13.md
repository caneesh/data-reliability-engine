**Major unknowns.** The service account's grants (the real runtime read-only guarantee); the Spark settings that decide whether the HMAC secret and key strings sit in plain form on executors; real table sizes and open-key counts; and the spec questions in section 9, several of which (closed windows and late writes, due-ness in RERUN and REPLAY, what "latest load time" means for a key) change what the engine should do.

### What the static guard cannot prove, and what the platform must provide

The scanner is regex over text. Blind spots: a write statement built from pieces or held in a variable; `getattr(df, "write")`; RDD save APIs (`saveAsTextFile`, `saveAsHadoopFile`, `saveAsObjectFile`); `FileSystem.create` via `_jvm`; `open(..., "w")` and `Path.write_text` (explicitly allowed); `subprocess.run` with a variable; `CREATE TEMPORARY FUNCTION … USING JAR`; Hive UDFs with side effects. Since every configured-text `spark.sql` is a query, rule 1 ultimately rests on the service account: SELECT only on production databases, read on landing and log paths, write only on the dq database, with Ranger or HDFS ACLs denying writes elsewhere. Spec section 11 lists "read-only account with write only to `dq`" as a platform decision; it should also list the grants explicitly and the Spark settings in the UNVERIFIED list below.

### Checked and found sound (non-functional)

One write path with column reorder before `insertInto` (`tests/test_writer.py`); retention bounds (`tests/test_retention.py`); `dre run` never creates the database or store (`tests/guard/test_no_database_creation_in_run.py`, `test_ddl_only_through_install.py`); `dre guard` grants no allowances; `error_detail` wherever an exception is logged or stored; probe evidence holds paths, counts and parsed values, never log lines or file contents (`causes/probes.py:159-168`); `Failure.key["k"]` stays in memory; HMAC secret read once, unreadable or empty → exit 3 before any write; stdout sink prints counts unless `full_body: true` (A11 holds); identifier and hex validation on every id interpolated from dq rows; `SandboxedEnvironment` + `StrictUndefined` for conf templates; a failing extension import is rolled back and becomes a config error (`tests/test_extensions.py::test_an_extension_that_fails_half_way_is_rolled_back`); sinks are isolated per sink (`notify/sinks.py:140-149`); A1 to A11 show no regression.

### UNVERIFIED because they depend on the deployment

- Service-account grants and Ranger or HDFS ACLs (rule 1 at runtime).
- The HMAC secret on executors: the pickled UDF closure travels in the task binary and lives in every executor's Python worker memory, in plain form unless `spark.authenticate`, `spark.network.crypto.enabled` and `spark.io.encryption.enabled` are set. Not in the event log or UI. Not documented in README or decisions.
- Key strings on executor local disks: `localCheckpoint()` and shuffle spill write canonical key strings to `spark.local.dir` for the application's lifetime; inherent to Spark over these tables, mitigated only by `spark.io.encryption.enabled`.
- Spark UI and history-server retention of plan text (N2); `spark.sql.redaction.string.regex`.
- Hive concurrent-append safety into one `run_date` partition (N5).
- Driver-host permissions on `hmac_secret_file` and the conf directory; client deploy mode's Python version.
- Scheduler handling of exit code 1 (uncaught) versus 2 and 3; the watchdog scheduled from a separate host as spec section 8 requires.

## 5. End-to-end data-loss scenarios

The engine compares adjacent layers only where a dataset has a `key_map` (spec section 1: no reconciliation across every layer in release 1). What it can and cannot tell apart today, with the evidence each verdict rests on:

| Stage | What can go wrong | What the engine sees | Evidence it stores | What it cannot tell apart |
|---|---|---|---|---|
| **File landed, not loaded to raw** | The pipeline stalled, the file is unreadable, a stopper file holds the load, the cursor skipped it | T1_FILES_NOT_LOADED (files first seen more than `sla_hours` before the window end with zero raw rows by base file name), T1_ON_TIME (a slot with no load) | `dq_file` (first seen, sizes), the raw row count per file name, cause rows PIPELINE_STALLED, UNREADABLE, RAW_LOAD_HELD, SKIPPED_BEHIND_CURSOR, LOAD_ERROR (probe evidence: paths, counts, parsed values) | A file whose raw rows carry a different file name than its path (matching is by base name only); a file registered again after its `dq_file` row aged out (P9) |
| **Raw to curated, per file** | Rows dropped, a whole file skipped, rows rejected by filter rules | HOP_FILE_COMPLETENESS (`dn_rows < up_rows` per file after both `feed_filter`s, excluded rows counted apart), causes FILE_SKIPPED, INVALID_KEY, NOT_RUN, FILTERED, REJECTED | per-file counts in `detail`, cause evidence | A downstream that deduplicates (false FAILED) or duplicates (silent PASS) rows of a file (F5); legitimately filtered rows unless `hop_exclusions` expresses the rule or `table_contains` points at the rejects table (needs developer question 6) |
| **Curated to gold, per key** | A key missing, an older version kept, a key wrongly matched | HOP_KEY_CURRENCY per key: MISSING, STALE, UNASSESSABLE, CURRENT; HOP_VALUE_AGREEMENT on owned columns; causes NOT_RUN, KEY_MISMATCH, JOIN_UNMATCHED, TIE_RESOLVED_BY_RULE, OLDER_VERSION_WRITTEN_LATER, NO_UPSTREAM_DATA, WRONG_PARTITION | `dq_key_event` (FLAGGED, STILL_FLAGGED, CLEARED per key hash; `key_value` only here), cause rows per `failure_ref` (at most 100 per evaluation) | **Missing versus filtered:** only `hop_exclusions` (a predicate on the upstream) or a rejects table distinguishes them. **Missing versus delayed:** a key is pending until `latest load + sla_hours`; after that, delay and loss look the same until the key arrives (then CLEARED) or NOT_RUN's load-time evidence says the load never ran. **Aggregated:** only through a `derived` upstream contract at the declared grain, with JOIN_UNMATCHED for left-join misses. **Duplicate:** not at the hop; T1_KEY_DUPLICATES on a `key_unique` dataset, and tied upstream versions surface through TIE_RESOLVED_BY_RULE. |
| **Within a layer over time** | Nulls in key columns, out-of-range values, a short or missing load, a silent schema change | T1_KEY_NULLS, T1_COLUMN_RANGE, T1_ZERO_ROWS, T1_VOLUME (against 14 earlier loads of the slot), T1_SCHEMA_DRIFT, T1_FRESHNESS | counts and the slots in `detail` | Rows written with a load time inside an already-closed window (F9); the DST hour (F3) |
| **The engine itself** | A result not stored, key events not stored, a cause not stored, a run that died | `evidence_incomplete` marker, PARTIAL status, held windows, pending investigations retried for 7 days, watchdog | `dq_run`, marker rows, `v_latest_run` | A grouped evaluation partly marked hides its sibling group until the next run (F2); two overlapping runs duplicate evidence (N5) |

**Evidence required to distinguish the five cases**, in words: *missing* needs the key (or file) present upstream after `feed_filter`, past its SLA, absent downstream, and no exclusion or rejects match. *Filtered* needs the exclusion predicate or a rejects-table row for the ref. *Aggregated* needs a declared grain (the `derived` contract) so the comparison is at that grain. *Delayed* needs the load time of the newest downstream load to be older than the upstream load (NOT_RUN) or the key to be inside its SLA (pending). *Duplicate* needs a `key_unique` declaration (T1_KEY_DUPLICATES) or tied upstream versions (TIE_RESOLVED_BY_RULE). The first two are where the configuration is still incomplete (`hop_exclusions`, `probes.filter_rules`, `probes.rejects` are `null` in the sample, so FILTERED and REJECTED return NOT_READY), which is the right behaviour until developer question 6 is answered.

## 6. Performance analysis

**Workload assumptions** (from spec section 11 and the sample conf; no timings are invented): one FILE_CYCLIC feed with six loads a day; three datasets (raw partitioned by file date, curated with several versions per key, gold with a four-part key); hourly NORMAL runs; a weekly full sweep; `dq` retention of 84 months for results and events and 13 months for the file registry; `compute_budget_minutes` per dataset.

**Where the cost goes, per hourly run, as the code stands.**

1. **Store maintenance before any check** (P14): the window history and the rule schedule read all of `dq_check_result` with no partition bound; file count grows by about one ORC file per evaluation per run.
2. **Landing** (P7): a recursive listing of every file-pattern root in the plan, due or not, with several JVM calls per file; the feed's registered paths collected from a window over all of `dq_file`.
3. **Tier 1 checks on a due dataset** (P4, P11, P13): each windowed check reads the whole table; the slot checks nested-loop the table against the slot list; duplicates do a whole-table GROUP BY.
4. **Hop checks** (P3, P16, P1): the upstream read about ten times and the downstream several times per hop per window, each under a whole-table window function; a derived upstream re-aggregated inside each; the open-key view window-functioned over the whole event table.
5. **Causes** (P5, P12, H1, P15): unbudgeted; a rejects table hashed in full per FAILED result; log globs collected; the landing registry and raw table re-aggregated; pending investigations re-run hourly for a week.
6. **Digest** (P2): every flagged key hash of the run collected to the driver.

**Scale thresholds in words.** None of the above depends on window length; every term is proportional to full table size, open-key count or event-table size. The hourly run stops fitting in the hour when the curated and gold tables reach the size at which one whole-table window function takes minutes (then multiplied by ten per hop), or when the open-key set reaches millions (P1, P2). The compute budget then turns hop checks into DID_NOT_RUN / budget_exceeded every hour, holds the window, and after `max_window_hours` records a WINDOW_GAP: the engine fails safe, but it stops watching. The two levers with the largest effect are P4 (partition pruning, which makes every windowed scan proportional to the window) and P3 (candidate keys before the window functions, one shared judged view per hop).

**Proposed benchmarks** (synthetic, from `tests/e2e/build_synthetic.py` scaled up): (a) `EXPLAIN FORMATTED` of each rendered template on a partitioned synthetic table, asserting `PartitionFilters` once P4 is in; (b) a hop over a curated table of N keys × V versions with an open set of M keys, timing one evaluation and one full sweep before and after P3 and P1; (c) `dq_check_result` with a year of synthetic rows across 365 partitions, timing `window_histories` and `last_completed` before and after P14. Report the measured times with the data shape; do not extrapolate from local mode to the cluster.

**Spark plans inspected during this review** (local mode, synthetic): the judged hop query scans the upstream three times and the downstream twice, each as `CatalogFileIndex` without `PartitionFilters` or `PushedFilters` (P3); a T1_KEY_NULLS scan on a day-partitioned table shows no `PartitionFilters`, and the same scan with a raw predicate on the partition column prunes to one of three (P4); the slot checks plan as `BroadcastNestedLoopJoin LeftOuter BuildLeft` with the range condition (P11).

## 9. Unresolved spec questions

Stop points, not guesses. Each changes what the engine should do.

1. **Section 4, closed windows and late writes.** Rows whose `load_time` lies in an already-closed window are never re-read (F9). Should `settle_minutes` be required to exceed the longest write, or should load-window checks re-read the previous window?
2. **Section 4, due-ness in RERUN and REPLAY.** The text says RERUN evaluates every dataset planned and REPLAY replays recorded windows exactly; the code gates both on due-ness with no file changes (F1). Which is intended?
3. **Section 6, "its latest load time plus sla_hours".** The key's latest load time, or the load time of its latest version (F4)?
4. **Section 6, HOP_FILE_COMPLETENESS.** Is row-count preservation per file an intended assumption, and should `dn_rows > up_rows` be reported (F5)?
5. **Section 4, DST.** A time column in a DST zone with no offset is ambiguous for one hour a year (F3). Which reading is wanted, and should `dre validate` warn?
6. **Section 4 and 5, cause rows from historical runs.** Should RERUN and REPLAY write `dq_cause_result` rows under the NORMAL `evaluation_id` (F7)?
7. **Section 8, overlapping runs.** Hold-and-re-evaluate as "died while STARTED", or refuse to start (N5, F10)?
8. **Section 5, first-seen after retention.** What should first-seen mean for a file still under its root after its registry rows aged out (P7, P9)?
9. **Section 6, STILL_FLAGGED per evaluation.** Keep writing one event per open key per evaluation (P1), or write only changes and derive "still open" in the view?
10. **Section 6, T1_KEY_DUPLICATES.** Per window (keys loaded in it) or whole table (P13)?
11. **Section 11, step 6.** `partition_column` plus a partition value format as a pruning predicate only, never as a load-time substitute (P4)?
12. **Section 4, a lookback bound** on the window-history and rule-schedule reads (P14)?
13. **Section 11, platform prerequisites.** Record explicitly: the service account's grants (SELECT on sources, read on landing and log paths, INSERT on dq only, no HDFS write); the Spark settings for secret and key-string exposure on executors (`spark.authenticate`, `spark.network.crypto.enabled`, `spark.io.encryption.enabled`), plan redaction (`spark.sql.redaction.string.regex`), and dynamic allocation keeping executors with cached blocks.
14. **`docs/decisions.md` line 47** still says CONFIGURATION holds a window; the spec and the code say it never does (D1). Which is current?

The values section 11 lists as unknown (the real RMS paths, stopper and handoff files, the rejects table, the gold merge and dedupe clauses, the CDC table) stay unknown; nothing in this review invents them.
